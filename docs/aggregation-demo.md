# CISA and post-quantum proof aggregation

The repository now runs two aggregation experiments. Schnorr CISA produces the
small expected aggregate signatures. A separate leanVM experiment produces
real hash-based proofs of XMSS signatures and binds their claims to synthetic
Bitcoin payments. The proof experiment's overhead is large for small batches.

The roles remain distinct:

| Component | What it contributes |
| --- | --- |
| P2MR | A commitment to spending scripts with no EC key-path bypass. |
| SHRINCS or another PQ signature | Authorization by the owner. |
| Transaction-aware verifier | Binding authorization to actual inputs, values, outputs, and script. |
| Covenant | Additional constraints on where a transaction may send its outputs. |
| Compatible aggregation | A shared authorization object for multiple inputs. |

The native SHRINCS opcode already binds the transaction. It does not need a
covenant for that purpose. Covenants can add spending policies. Schnorr CISA
cannot combine SHRINCS signatures; proving many hash signatures is a different
route to a shared authorization object.

## Executed Schnorr CISA

```sh
python -m btc_pq.cisa_demo --fetch
python -m unittest tests.test_cisa_demo -v
```

This uses the unmodified half-aggregation, full-aggregation, signing, and
message functions from [BIP460 PR 2212 at the pinned revision](https://github.com/fjahr/bips/tree/855b4ccfbebd07554c1e400415467b62d2b40713/bip-0460).
It also reproduces that revision's complete wallet-vector JSON exactly.
The local verification model handles all-input groups with `SIGHASH_DEFAULT`;
it is not a general BIP460 consensus implementation and does not claim to run
all of the proposal's consensus vectors.

| Inputs | Mode | Signature data, including marker | Whole tx bytes | Weight | vB |
| ---: | --- | ---: | ---: | ---: | ---: |
| 2 | Plain Schnorr | 128 | 269 | 674 | 169 |
| 2 | Half aggregation | 97 | 238 | 643 | 161 |
| 2 | Full aggregation | 65 | 206 | 611 | 153 |
| 10 | Plain Schnorr | 640 | 1,125 | 2,514 | 629 |
| 10 | Half aggregation | 353 | 838 | 2,227 | 557 |
| 10 | Full aggregation | 65 | 550 | 1,939 | 485 |

Half aggregation combines ordinary signatures without another signing round.
Full aggregation runs the interactive nonce/partial-signature protocol. Its
64-byte aggregate has a one-byte marker in this transaction encoding. These
are actual generated bytes, not just size formulas.

All [66 payment cases](../results/cisa-demo/report.json) match expectations.
Changed outputs, input outpoints, spent amounts, sequences, version, locktime,
signatures, input order, and missing authorization fail. Additional tests
check malformed witness shapes and aggregation-mode binding.

This remains Schnorr cryptography. BIP460 explicitly leaves Script signatures
unaggregated, and its current witness-v2 allocation conflicts with P2MR's
allocation. They need proposal coordination before deployment together. A
[native Bitcoin reference implementation is an open PR](https://github.com/bitcoin/bitcoin/pull/36122),
not evidence of mainnet activation. The local CISA experiment is separate from
the P2MR native builds.

## Executed hash-based proof aggregation

```sh
python -m btc_pq.pq_aggregate --build --counts 2,10,256
python -m btc_pq.pq_aggregate --outdir results/pq-aggregate/large --counts 512
python -m btc_pq.pq_aggregate --replay
python -m btc_pq.pq_aggregate --replay --outdir results/pq-aggregate/large
python -m unittest tests.test_pq_aggregate -v
```

The build pins [leanVM](https://github.com/leanEthereum/leanVM/tree/574521665891ad040580833d3cae62c9bd347c9b)
and uses its unmodified XMSS signer and aggregation prover/verifier. This XMSS
variant uses BLAKE2s, 32-byte public keys and 1,208-byte signatures. It is a
different scheme from our SHA256 SHRINCS-B32 integration. The proof machinery
is hash based; this experiment is not an independent analysis of its quantum
soundness or parameter security.

For each input, a P2MR script commits to the expected XMSS public key. The host
recomputes a domain-separated BIP341/342 digest from the actual transaction,
spent outputs and script, then supplies the expected `(key, epoch, message)`
claims to the native proof verifier. Each input has a different test key and
epoch, allowing distinct transaction signature messages. It does not accept a
prover's self-selected list of claims as sufficient payment authorization.

The Rust bridge generates individual signatures, creates a real aggregate
proof, serializes it, reloads it with the host's expected claims, and verifies
it. No boolean placeholder or hash of the signatures substitutes for a proof.

| Inputs | Original XMSS signatures | Proof excluding known claims | Proof including claims |
| ---: | ---: | ---: | ---: |
| 2 | 2,416 B | 229,952 B | 230,120 B |
| 10 | 12,080 B | 230,464 B | 231,240 B |
| 256 | 309,248 B | 316,616 B | 336,088 B |
| 512 | 618,496 B | 330,224 B | 369,152 B |

These [saved measurements](../results/pq-aggregate/report.json) include 36
transaction expectations. The [512-input run](../results/pq-aggregate/large/report.json)
adds 12 more and reduces authorization bytes by 46.6% excluding known claims,
or 40.3% including them, compared with its original XMSS signatures. This is
an observed crossover between the tested 256- and 512-input cases, not an
exact general break-even point. Altered payment fields, input order, annex, keys,
funding, and proof bytes fail. Timings in the report are single local runs,
including cold prover setup, while other research jobs were active; they are
not statistically controlled performance benchmarks. Proof sizes refer to the
actual saved objects.

The proof is stored outside the transaction in this experiment. The model's
local script marker is not an implemented opcode. Bitcoin would need a
transaction-level proof rule or another suitable verifier and encoding; these
large proofs do not fit our existing SHRINCS opcode's witness contract. The
reported proof sizes exclude the transaction, script/control-path framing and
any new protocol overhead. They must not be read as deployable transaction
sizes or fees.

For a two-input payment, direct SHRINCS remains much smaller in these demos.
Proof aggregation is a batch optimization with significant fixed overhead.
Supporting SHRINCS itself requires a SHA256 SHRINCS verifier inside the proof
system; that is not provided by leanVM's existing BLAKE2s XMSS circuit. The
[exact SHRINCS proof program](shrincs-proof.md) now provides that verifier and
passes six zkVM execution checks. Receipt generation and batch crossover are
tracked separately from those execution results.
